# MF/SIF Fund Comparison — Design

## Summary

Add a fund-comparison feature to the MF Screener (`app/screener/page.js`), modeled on the existing PMS comparison feature (`app/pms-screener/PMSCompare.jsx`), but covering **both** mutual funds and SIFs in a single, mixable comparison (up to 3 funds, any combination of MF and SIF). Compared to PMS, this feature adds: risk metrics (volatility, max drawdown, return/risk ratio), a real SIP-based Wealth Simulation (not just lumpsum), a category peer-rank (in place of PMS's APMI-specific Quartile Ranking, which has no MF/SIF equivalent data source), and a new interactive growth chart with hover-crosshair and click-drag range selection.

## Background

**PMS comparison pattern** (`app/pms-screener/PMSCompare.jsx`): a checkbox column in the strategy table (max 3 selections) feeds a floating `PMSCompareBar` ("N/3 selected" + "Compare Now"), which opens `PMSCompareModal` — a CSS-grid comparison table with sections (Returns, APMI Quartile, Alpha vs Benchmark, Wealth Simulation, AUM) and a weighted "Overall Leader" verdict banner at the end. This exact selection mechanic (checkbox column → floating bar → modal) is being ported directly.

**MF screener data** (`app/screener/page.js`): each MF fund object already carries precomputed `ret_1m/3m/6m/1y/3y/5y/7y/10y/inception`, `vol`, `max_dd`, `ret_per_risk`, plus `code` (for `/api/mf?code=X` NAV history), `name`, `category`, `amc`, `isin`. No AUM field exists in this app's MF dataset (AMFI's daily NAV feed doesn't include it, unlike APMI's PMS data) — **AUM is out of scope** for this feature.

**SIF screener data**: SIF schemes (`sifSchemes`, from `/api/sif-nav`) currently carry only `scheme_id`, `nav_name`, `sif_name`, `category`, `type`, `nav`, `nav_date` — **no precomputed period returns, volatility, or drawdown exist yet**, since SIFs are a new asset class (launched 2024-25) with as little as ~9 months of history for the oldest schemes. Real NAV history is available on-demand via `/api/sif-history?sd_id=X&from=...&to=...` (already used by the existing `SifDetail` drawer for its sparkline).

**Reusable engine**: `lib/xirr.js` exports a shared, validated `xirr(flows)` Newton-Raphson/bisection solver — the same algorithm `app/backtest/page.js` uses internally (that file's copy stays untouched; this feature imports the shared one, avoiding any risk to the existing backtest page).

## 1. Selection & entry points

A single `compareList` state (array, max 3 entries, each `{ type: 'mf' | 'sif', ...rawFundObject }`) lives in `ScreenerPage` (`app/screener/page.js`), persisting across MF/SIF tab switches. Both the MF table and the SIF table get a `⚖` checkbox column (identical markup/behavior to PMS's), each calling a shared `toggleCompare(fund, type)`. A `MFCompareBar` (new component, modeled on `PMSCompareBar`) floats at the bottom whenever `compareList.length > 0`, showing chips (name + a small type badge) and a "Compare Now" button (disabled below 2 selections). Clicking it opens `MFCompareModal`.

## 2. Data normalization

Before rendering, the modal maps every `compareList` entry into a common shape via `normalizeFund(entry)`:
- **MF** (`type: 'mf'`): direct field mapping — `{ id: 'mf-' + code, type: 'mf', name, house: amc, category, logoPath: getMFLogoFromSchemeName(name), ret_1m...ret_inception, vol, max_dd, ret_per_risk, navFetchKey: code }`.
- **SIF** (`type: 'sif'`): `{ id: 'sif-' + scheme_id, type: 'sif', name: nav_name, house: sif_name, category, logoPath: getSIFLogo(sif_name), ret_1m: null, ..., vol: null, max_dd: null, ret_per_risk: null, navFetchKey: scheme_id }` — the return/risk fields start `null` and get filled in once that fund's real NAV history resolves (see below); until then, the Returns/Risk table shows "—" for that fund exactly as it would for any fund missing a given period.

On modal open, for every entry with `type === 'sif'`, fetch `/api/sif-history?sd_id={navFetchKey}&from={365 days before today}&to={today}` (the exact same 1-year window `SifDetail`'s existing sparkline fetch already uses — comfortably covers "since inception" for every current SIF, all of which are under a year old) and compute `ret_1m/3m/6m` (and longer periods too, whenever the fetched series is long enough — the calculation naturally yields `null` for any period exceeding the fund's real history) plus `vol`/`max_dd`/`ret_per_risk` from that series, using the same point-to-point CAGR / monthly-stdev / peak-to-trough logic the MF screener's own build step already uses conceptually (reimplemented here as a small pure function, since the MF versions are precomputed server-side and not directly callable). This fetch is independent per fund (a failure only blanks that one fund's derived stats, not the whole modal).

## 3. Modal sections (top to bottom)

1. **Header row**: logo (`ProviderAvatar` + `logoPath`), name, house, category, a "🏆 Best in N metrics" badge, remove button — mirrors PMS's header row.
2. **Interactive chart**: growth of ₹1,00,000 invested, one line per fund, all normalized to start from the same date — specifically, the **latest** "first available NAV" among the selected funds (i.e. governed by whichever fund has the *shortest* real history), so every plotted line has genuine data across the full visible range. Requires each fund's real NAV history (already being fetched for SIF derivation above; for MF, fetched fresh via `/api/mf?code=X`, the same endpoint the fund detail drawer already uses). Hover shows a hair-line crosshair + tooltip (fund values at that date); click-and-drag selects a range, showing live start/end date pills while dragging, and on release shows each fund's % change over that exact window both in a floating on-chart panel and a panel below the chart — the shaded selection and both panels persist until the user taps/clicks elsewhere on the chart (which clears it and returns to hover mode). Touch-friendly via `touch-action: pan-y` (allows normal vertical page scroll while horizontal drag is captured for range selection) plus `touchstart`/`touchmove`/`touchend` handlers mirroring the mouse ones. This exact interaction was prototyped live and approved during brainstorming.
3. **Returns across all periods**: 1M through Inception, per-cell "best" highlight (only among funds that have non-null data for that period), a period's row hidden entirely only if every selected fund lacks data for it.
4. **Risk metrics**: Volatility, Max Drawdown, Return/Risk ratio — same per-cell "best" highlighting (lowest is "best" for volatility/drawdown, highest for return/risk ratio).
5. **Category peer-rank**: for each fund, its rank within its own type+category pool by 3Y return (e.g. "#3 of 47 in Flexi Cap Fund" for an MF; "#2 of 6 in Equity Long-Short" for a SIF) — computed client-side from the already-loaded `funds`/`sifSchemes` arrays filtered to the same `type` and `category`, no new fetch needed. A fund's own rank is independent of what else is in the comparison.
6. **Wealth Simulation**: two rows —
   - **₹1,00,000 lumpsum**: formula-based using each fund's existing annualized CAGR figures (1Y/3Y/5Y stops), same math as PMS's `fmtWealth` — appropriate here since a lumpsum's outcome genuinely is just its CAGR compounded, no sequencing effect.
   - **₹10,000/month SIP**: **real**, computed from actual historical NAV (not a CAGR-based approximation — SIP returns are sequence-dependent and a formula would misrepresent them). Reuses each fund's already-fetched NAV series (from the chart's fetch above), generates monthly SIP purchase dates (a fresh, comparison-scoped adaptation of `app/backtest/page.js`'s `sipDates`/`fwd` pattern — not extracted from that file, to avoid any risk to the existing backtest page), and computes the final value plus `xirr()` (imported from `lib/xirr.js`) for the resulting cash flows. Same 1Y/3Y/5Y stops as the lumpsum row, each labeled with its real SIP XIRR.
7. **Verdict banner**: same weighted, margin-aware scoring as PMS (`PERIOD_WEIGHTS`, skip periods with <2 participants, average by weight actually scored on) — extended to also skip a fund entirely from the Risk-metrics and Wealth-Simulation contributions to the score if that fund's data for those sections is still `null` (relevant for newer SIFs), so a young SIF isn't penalized for not existing long enough, exactly matching PMS's existing "average, not sum" fairness principle.

## 4. Error handling

Every async fetch (SIF-derived stats, MF/SIF NAV history for the chart and SIP sim) is per-fund and independently caught — a failure blanks only that fund's chart line / sim figures / derived stats (shown as "—" or "data unavailable"), never blocks or breaks the rest of the modal. This mirrors PMS's already-proven `.catch(() => ({ id, data: null }))` pattern for its benchmark/quartile fetches.

## 5. Testing approach

No test runner is configured in this repo (established convention). Verification: `npm run build` for a clean compile; standalone Node scripts covering the pure-logic pieces in isolation — the SIP simulation (monthly purchase generation + `xirr()` producing a sane result against hand-computed cases), the lumpsum formula, the weighted verdict scoring (including the "skip missing data" fairness rule), the category peer-rank computation, and the MF/SIF field-normalization mapping; and a manual browser walkthrough selecting a mix of MF and SIF funds, checking every section renders sensibly (including a SIF with only ~9 months of history correctly showing blanks for long periods), the chart's hover/drag/touch interactions, and mobile-width layout.
